# Deployment and release operations

The chart owns only the TrackApplyEasy service, workload, ServiceAccount, retained claim, NetworkPolicy and exact browser routes in namespace `trackapplyeasy`. It does not own Keycloak, gateway, DNS, certificates or shared Traefik. The private GitOps setup sources prepare those app-scoped prerequisites. No commands here authorize an unrelated cluster or old-server change.

## Prepare once

1. Verify context/node `personal-prod-2`, current capacity, recovery access, retained storage and existing Traefik/gateway identities. Create the app namespace/foundation under Research & Development. Use explicit `kubectl --context personal-prod-2` and Helm `--kube-context personal-prod-2` for all later live commands.
2. Through private Keycloak administration, create only the app's new scopes, two resource definitions and disabled confidential clients. Keep the realm closed. The browser callbacks are exactly `https://work.vvivid.dev/auth/callback` and `https://work.lab.vvivid.dev/auth/callback`; API audience is canonical public URL plus `/api/v1`. Attach an exact custom audience mapper that survives code exchange and offline refresh. Optional `offline_access` belongs only to these new clients. Access lifetime stays 300 seconds; do not change shared realm or other apps' settings. Confirm owner consent/role permits offline grants. Keep the MCP client absent/disabled until the intended client's actual callback and auth method are known.
3. Generate the stable session keyring and store `client-secret` and `session-keys.json` in the namespace Secret `trackapplyeasy-identity`, from protected files. Copy only the gateway's **public** JWKS into ConfigMap `trackapplyeasy-gateway-jwks`, key `public.jwks.json`. The chart's nonroot init invocation copies its mounted secret files into a memory-backed runtime volume as 0600 files. The main container does not mount the projected Secret directly.
4. Prepare app-specific DNS-01 Secret references/Issuers, prove staging issuance, then request the trusted public and private Certificates. Record actual readiness before setting either route readiness flag. Public and private ingress gates are independent. The private gateway route is a separate exact app object under the existing private entrypoint and uses an optimistic gateway-config patch preserving current routes.
5. Configure protected GitHub environments `artifact-publication` and `production-promotion` on this standalone repository. Publication uses only repository `GITHUB_TOKEN` with packages write. Promotion needs `GITOPS_APP_CLIENT_ID`, `GITOPS_APP_PRIVATE_KEY` and `TRACK_GITOPS_ENABLED=true`; scope that App to `VVivid/homelab-gitops`. No monorepo Tailscale or Zot credentials are used. Promotion changes only the fixed `environments/rd/trackapplyeasy/production/fleet.yaml` release fields.

## Publish, then enroll

Merge reviewed source to `main`, run checks, and push a new exact `vX.Y.Z` tag when publication is authorized. The workflow checks source ancestry, runs API/OIDC/SDK/SQLite/race/browser/chart checks, builds an AMD64 image and publishes `ghcr.io/vvivid/trackapplyeasy:X.Y.Z` plus `oci://ghcr.io/vvivid/charts/trackapplyeasy` version X.Y.Z. A version collision fails; CI never intentionally overwrites tags. Image deployment is digest-pinned; chart manifest digest is recorded provenance, while Fleet resolves the exact chart version. Authorized registry writers must preserve those version tags.

GHCR packages start **private**, including packages from public source repositories. After first publication an operator must set both the image package and chart package public, then independently prove anonymous reads. The promotion job deliberately verifies both anonymous digests before updating GitOps. Fleet receives no GHCR credentials; its existing private-Zot credential filter must stay unchanged. Missing credentials, false enable flag, private packages, digest mismatch, unconfigured desired state or concurrent GitOps modification stops promotion. Failed promotion can be rerun separately without republishing artifacts. `Retry existing release promotion` takes the exact nonsecret JSON record from the Publish job.

Before promotion, operators set `configured=true` in the fixed Fleet file only after identity/storage prerequisites. Keep route enablement false until trusted TLS and app acceptance. The source commit, image digest, chart version and chart digest must be concrete before app enrollment; defaults fail chart rendering. Add only the exact TrackApplyEasy foundation and production Fleet paths using a patch generated from the current live GitRepo resourceVersion/paths. Preserve all existing paths, credential selectors and paused state. Never apply a stale shared GitRepo manifest.

Enroll the verified owner explicitly using the protected-file CLI, then validate a real browser login on both hosts. Assert the original PDF bytes/hash, create a real application, append a dated response, inspect history/counts/analysis and restart exactly this one pod to confirm persistence. From an external public network prove `/mcp`, private hosts, `/health`, `/metrics` and unrelated paths are unavailable; prove trusted private HTTPS through Tailscale. Positive `GET /` or a passing build alone does not establish business acceptance. Actual intended MCP OAuth/consent/refresh/tool calls remain a separate gate.

## Recovery and backup

The claim uses a retained local class and Helm `keep`, with one writer and `Recreate`; replacements have brief downtime. A retained claim is not a backup or HA. The initial chart requests 5 GiB but local-path capacity is not a filesystem quota. Monitor disk and PVC contents. Preserve the claim, keyring, client secret and owner enrollment. Never delete a namespace/PVC/identity database to restart.

Use `scripts/backup.py` against a mounted database path to take a consistent SQLite online backup. It includes PDF blobs and encrypted sessions, runs integrity/foreign-key checks, and verifies every PDF SHA256 without printing data. Store the keyring and provider client secret separately with owner-only permissions and an independent backup destination. Database copies without WAL coordination or the stable encryption key do not establish recoverable sessions.

Before accepting recovery, restore a protected backup into an isolated directory/namespace with no second writer, verify integrity/hash and owner/application/history counts, then exercise authenticated PDF/history reads. Restore verification is not claimed until that drill runs. For rollback, disable only app routes or stop the app, preserve all state, then restore the last accepted image/chart. Schema-changing releases require a coherent database restore plan; an image rollback does not reverse committed writes. Current schema is version 2: opening a version 1 database transactionally adds CV `archived` (false) and `revision` (1), retaining all rows, PDF blobs and references. Take a coherent backup before the first upgraded start. Older version 1 binaries reject schema 2, so rollback requires stopping the writer and restoring the paired pre-upgrade backup; doing so discards later writes and must be an explicit recovery decision. Newer unknown schemas are rejected without lowering `user_version`. Session-key rotation retains old decrypt keys until every old session is renewed/expired; removing a live decrypt key forces those users to sign in again.
